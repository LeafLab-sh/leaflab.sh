# For agents working in this repository

The LeafLab website, [leaflab.sh](https://leaflab.sh): Astro on Cloudflare Workers.

## Commands

```bash
bun run dev          # Start dev server at localhost:4321
bun run build        # Build to ./dist/
bun run preview      # Build + run via Wrangler locally (simulates Cloudflare)
bun run deploy            # Build + deploy to Cloudflare (dev)
bun run deploy:production # Build + deploy to Cloudflare (production)
bun run cf-typegen   # Regenerate Cloudflare Worker type definitions
```

`bun run test` — runs Vitest. `astro check` runs as part of `bun run build`.

**Conventional commits are required.** Commitlint enforces the [Conventional Commits](https://www.conventionalcommits.org/) spec via a Husky commit-msg hook. Every commit message must follow the `type: description` format (e.g. `feat:`, `fix:`, `chore:`). This is what release-please uses to determine version bumps and generate the changelog.

## Architecture

**Astro + Cloudflare Workers** — Astro handles file-based routing and SSR; the `@astrojs/cloudflare` adapter compiles the output to run on Cloudflare Workers at the edge.

- `src/pages/` — File-based routes (`.astro` files map directly to URL paths)
  - `src/pages/robots.txt.ts` — Dynamic API endpoint that serves `robots.txt` pointing crawlers to the sitemap
- `src/layouts/` — Reusable HTML shell templates
- `src/components/` — Astro components
- `src/env.d.ts` — Extends `App.Locals` (logger) and declares `ImportMetaEnv` vars; Cloudflare bindings are accessed via `import { env } from "cloudflare:workers"` in middleware
- `src/middlewares/` — `cloudflare-access.ts` (Cf-Access JWT validation), `logger.ts` (attaches logger to locals)
- `src/utils/` — Custom structured JSON logger (`logger.ts`)

Build output splits into `dist/client/` (static assets) and `dist/server/` (Worker chunks). Wrangler serves the `dist/` directory via the `ASSETS` binding and routes dynamic requests to the Worker.

**Cloudflare bindings** (KV namespaces, D1 databases, etc.) are declared in `wrangler.jsonc` and typed via `worker-configuration.d.ts` (auto-generated by `bun run cf-typegen`). Access them via `Astro.locals.runtime.env` in `.astro` files or `context.locals.runtime.env` in API endpoints.

**Astro integrations** configured in `astro.config.mjs`:

- `@astrojs/sitemap` — generates `/sitemap-index.xml` at build time; `site` is read from `SITE_URL` env var, falling back to `https://leaflab-website-dev.leaflab.workers.dev`; `deploy:production` sets `SITE_URL=https://leaflab.sh` via `cross-env` before building
- `@astrojs/partytown` — offloads third-party scripts to a web worker; opt scripts in with `type="text/partytown"`

**Platform proxy** is enabled in `astro.config.mjs`, so `bun run dev` simulates the Cloudflare runtime locally without needing to deploy.

Wrangler environments are configured in `wrangler.jsonc`: the default environment targets `leaflab-website-dev` (`leaflab-website-dev.leaflab.workers.dev`, no custom domain); `--env production` targets `leaflab-website` with the `leaflab.sh` custom domain.

## Release & Deployment

Releases are automated via [release-please](https://github.com/googleapis/release-please) (`.github/workflows/release-please.yml`):

1. Every push to `main` triggers release-please, which reads conventional commits since the last release and opens (or updates) a release PR that bumps `package.json` and updates `CHANGELOG.md`. Merging it tags `vX.Y.Z` and creates the GitHub release. release-please acts as the `leaflab-automation` App, the only actor the org lets create `v*` tags (`standards/releases`), so nobody tags by hand. Tags up to `leaflab-website-v0.13.0` used the old format; `bootstrap-sha` in `release-please-config.json` bridges to the first `v*` release.
2. Every push to `main` also triggers an automatic deploy to `leaflab-website-dev` (`leaflab-website-dev.leaflab.workers.dev`) via the Cloudflare app integration (not a GitHub Actions job).
3. When the release PR is merged, `deploy-production` runs and deploys to the `leaflab-website` Cloudflare Worker with the `leaflab.sh` custom domain, via the `production` GitHub environment.

The production deploy job requires two secrets: `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.

## Working in LeafLab-sh

This repository follows the LeafLab-sh org's standards. They're specified in the org spec store, [`LeafLab-sh/openspec`](https://github.com/LeafLab-sh/openspec) (store id `leaflab`). This section says where to find them, not what they all say.

### Process

- **Commits** (`standards/commit-messages`): Conventional Commits, a `Refs: LEA-<n>` footer for Linear work, and no `fixup!` commits left on `main`.
- **Pull requests** (`standards/pull-requests`): open as a draft, and mark ready after self-review once CI passes. Fix findings with `fixup!` commits and autosquash before merging. Link Linear with `Fixes LEA-<n>` or `Part of LEA-<n>` in the body. Merge by rebase only.
- **Branches** (`integrations/linear`): `lea/lea-<n>-<slug>`, named after the Linear issue.

### Reviewing specs

This project's own specs are in `openspec/specs/`:

```sh
openspec list --specs
openspec show <spec-id> --type spec
```

The org's specs are in the `leaflab` store, which `openspec/config.yaml` references. Pull your clone of the store first, because OpenSpec never does. `openspec context` shows where the clone is.

```sh
openspec list --specs --store leaflab
openspec show <spec-id> --type spec --store leaflab
```

If `openspec doctor` reports the `leaflab` reference as unresolved, clone and register the store as its README says.

### Contributing to specs

- **This project's behavior:** an OpenSpec change in this repository. Use `/opsx:propose` (or `openspec new change <id>`), pass `openspec validate <id> --strict`, and run `openspec archive <id>` in the pull request that implements it.
- **An org standard, an integration, or how repositories are set up:** an OpenSpec change in `LeafLab-sh/openspec`, by pull request there. Never write the store from this repository.
